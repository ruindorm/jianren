# 圖片生成流程

本作品所有 AI 生成圖片的產出方式、工具位置、參數原則與成本紀錄。

---

## 原則（預設值，不需要每次重講）

**1. 比例先決定。** 動手之前先問「這張圖要用在哪裡」，由用途決定 `aspect_ratio`。
沒有預設值——`gen-image.ps1` 把 `-AspectRatio` 設成必填，就是為了逼自己先想清楚。

**2. 風格依任務而定。** 寫實、像素、線稿、插畫沒有高下之分，只有適不適合那個位置。
同一部作品可以有多套視覺，見下方〈風格對照〉。

**3. 品質一律最低。** `quality=low` + `resolution=1K` 是**固定預設**，
不是偷懶，是實測後的結論。除非明確要求高解析輸出（印刷、大圖 banner），
否則不要動這兩個參數。

> 最低品質下 AI 的表現已經很好，而且成本差距是數十倍等級——證據見下方成本表。

---

## 成本實測

同一支模型（`openai/gpt-image-2`），同樣 2:3，只差品質與解析度：

| 參數 | 花費 | 耗時 | 文字準確度 | 備註 |
|---|---|---|---|---|
| 2K / high | **USD 0.1667** | 3 分 30 秒 | 兩個英文字糊掉 | 寫實系封面 |
| **1K / low** | **USD 0.0036** | **33 秒** | **全部正確** | 像素風封面 |

**便宜 46.9 倍，快 6.4 倍，而且文字反而更準。**

以 USD 10 的餘額換算：

| 參數 | 可生成張數 |
|---|---|
| 2K / high | 約 60 張 |
| 1K / low | **約 2,700 張** |

計價方式是 token 制（輸出 USD 22.5 / 1M image tokens，輸入 USD 3.75 / 1M），
所以實際金額隨圖片內容浮動，上表是實測值。

推估中間值（依 OpenAI 公布的 image token 數換算，未實測）：

| 參數 | 估計花費 |
|---|---|
| 1K / low | ~$0.004 |
| 1K / medium | ~$0.015 |
| 1K / high | ~$0.06 |
| 2K / high | ~$0.17 |

## 工具位置

| 工具 | 路徑 | 用途 |
|---|---|---|
| 生成 | `tools/gen-image.ps1` | 呼叫 Pika API 產圖，預設 1K/low |
| 壓縮 | `tools/compress-image.ps1` | 產出 webp / jpg / 平台縮圖 |
| 合成字幕 | `tools/compose-subtitle.ps1` | 台詞合成到畫面下方 1/4 |
| 金鑰 | 環境變數 `PIKA_API_KEY`，或 `JIANREN_ENV_FILE` 指向的 `.env` | **絕不進版控、絕不印出** |
| ffmpeg | PATH，或環境變數 `FFMPEG_PATH` | 壓縮與縮放 |

**這是公開倉庫，所以腳本裡不寫死本機絕對路徑。** 路徑一律走環境變數，一次設定：

```powershell
setx PIKA_API_KEY      "你的金鑰"          # 或用下面那行指向 .env
setx JIANREN_ENV_FILE  "你的路徑\.env"
setx FFMPEG_PATH       "你的路徑\ffmpeg.exe"
```

金鑰解析順序：`PIKA_API_KEY` → `-EnvFile` 參數 → `JIANREN_ENV_FILE` → 倉庫根目錄 `.env`。

環境沒有 ImageMagick，本機縮放一律走 ffmpeg。
（CI 的 Ubuntu runner 有 ImageMagick，那是建置流程的 fallback 封面用的，與這裡無關。）

## 用法

```powershell
# 1. 生成（比例必填，品質預設最低）
.\tools\gen-image.ps1 -PromptFile prompt.txt -AspectRatio 2:3 -Out assets/cover-en-raw.png

# 2. 壓縮出各平台版本
.\tools\compress-image.ps1 -In assets/cover-en-raw.png -Name cover-en

# 像素風一定要加 -Pixel（改用 nearest-neighbor 縮放）
.\tools\compress-image.ps1 -In assets/cover-en-pixel-raw.png -Name cover-en-pixel -Pixel
```

生成腳本會在送出前印出餘額與設定，結束後印出實際花費與剩餘餘額。

## API 規格

來源：`https://dev.pika.art/llms.txt` 及各 operation 的 spec。
**不要憑印象猜端點或欄位**，以 catalog 為準：
`GET https://api.dev.pika.art/catalog/apis/{api_id}?expand=inputs`

```
Base URL : https://api.dev.pika.art
Header   : X-API-Key: $PIKA_API_KEY
Submit   : POST /v1/media/openai/gpt-image-2/text-to-image
           POST /v1/media/openai/gpt-image-2/image-to-image   ← 參考圖與局部重繪
Poll     : GET  /v1/media/jobs/{id}          → status: queued|running|completed|failed
Result   : GET  /v1/media/jobs/{id}/content  → { "url": "..." }
餘額     : GET  /billing/balance             （免費，可用來驗證金鑰是否有效）
```

非同步。送出後必須輪詢到 `completed` 才能取內容。

### 可用參數

| 參數 | 值 | 預設 | 影響價格 |
|---|---|---|---|
| `prompt` | string（必填） | — | 輸入 token |
| `aspect_ratio` | 1:1 / 2:3 / 3:2 / 3:4 / 4:3 / 4:5 / 5:4 / 9:16 / 16:9 / 21:9 | 1:1 | 否 |
| `quality` | low / medium / high / auto | **low** | **最大** |
| `resolution` | 1K / 2K / 4K | **1K** | 次之 |
| `output_format` | png / jpeg / webp | png | 否 |
| `num_images` | 整數 | 1 | 線性倍增 |
| `background` | auto / opaque / transparent | — | 否（透明需 png/webp） |
| `size` | `WxH`，會覆蓋 aspect_ratio 與 resolution | — | 依尺寸 |

同平台其他可用影像模型：Nano Banana Pro、Seedream 5.0 Pro/Lite、Recraft 4.1、Grok Imagine。
**需要準確渲染文字時選 GPT Image 2**，這是它明顯強過其他家的地方。

## 編輯能力對照（image-to-image）

分鏡插圖走的是「多張參考圖 → 生成」，所以編輯端點的參數比 text-to-image 更關鍵。
以 catalog 實查為準：

| 模型 | 端點 | 多參考圖 | mask | quality | resolution |
|---|---|---|---|---|---|
| **GPT Image 2** | `openai/gpt-image-2/image-to-image` | `image_urls[]` | **✓ `mask_image_url`** | ✓ low/medium/high | 1K/2K/4K |
| Nano Banana Pro | `google/gemini-3-pro-image/image-to-image` | `image_urls[]` | ✗ | ✗ | 1K… |
| Grok Imagine Image Quality | `x-ai/grok-imagine-image-quality/image-to-image` | `image_urls[]`（**文件寫最多 3 張**） | ✗ | **✗ 無此參數** | 1K/2K |

其他還有 Seedream 5.0 Pro/Lite、Seedream 4.0、Nano Banana 2、Nano Banana 2 Lite、Grok Imagine，
全部都是 `image_urls[]` 形式的編輯端點。

**整個平台沒有任何 controlnet / pose / depth / strength 參數。**
構圖草稿只能當「參考圖之一」送進 `image_urls`，是軟性引導，不是硬性幾何鎖定。

### 為什麼 mask 值錢

同一個機位換表演變體時，不要重生整張——**鎖住背景與身體，只開臉部與手部重繪**。
構圖與服裝物理上不可能漂移。目前只有 GPT Image 2 支援，mask 必須是**含 alpha 通道的 PNG**，
缺 alpha 會被供應商直接拒絕。

### Grok 沒有比較靈活

傳聞相反：就參數面而言 Grok 的編輯端點比 GPT Image 2 **少**——沒有 mask，也沒有 quality。
它唯一明確勝出的是文件寫死「最多 3 張來源圖」，而 GPT Image 2 的上限未公開。
`aspect_ratio` 列舉值比較多（含 1:2、2:1、9:19.5 等），但分鏡只用 16:9，用不到。

## 風格對照

| 位置 | 風格 | 理由 |
|---|---|---|
| **章節插圖／分鏡** | **日系漫畫風** | 作者裁示 2026-08-17。88% 的機位功能是看清一張臉，像素風最弱處正是小尺寸的臉；成本理由已隨 315 張 $1.13 失效。前綴見〈分鏡提示詞規範〉 |
| 中文平台封面 | 日系漫畫風（菱形分鏡格） | 與分鏡同風格。樣本 `assets/candidates/dia-a2-clean.png` |
| 英文平台封面 | 16-bit 像素風（現況，未同步） | RoyalRoad 首頁清一色寫實封面，像素風辨識度極高——**尚未依新畫風重做** |

> 舊表把「章節插圖＝像素風」的理由寫成成本（「14 章不到 $0.06」）。
> 那個理由在分鏡制度下已失效，見〈分鏡製作流程〉決策紀錄。
> **若作者要為特定作品或特殊鏡頭指定不同畫風，會另行提出；AI 不自行決定。**

## 壓縮

生成的原圖一律保留（`*-raw.png`），那是之後 image-to-image 改圖的母檔。
發布用的檔案全部由原圖壓出來：

| 輸出 | 用途 | 實測壓縮率 |
|---|---|---|
| `.webp` 全尺寸 | 網頁 | 比原 PNG 省約 89% |
| `.jpg` 全尺寸 | EPUB 封面、通用 | |
| `-400x600.webp/.jpg` | 平台縮圖 | |

**像素風必須用 nearest-neighbor 縮放**（`scale=...:flags=neighbor`）。
用預設的雙線性內插會把像素硬邊糊掉，整張變爛泥。

## 已知地雷

**EPUB 封面的副檔名要正確。** pandoc 靠副檔名判斷 mimetype，
若餵給它的檔案叫 `cover.img`，`content.opf` 會標成 `application/octet-stream`，
不符 EPUB 規範，多數閱讀器不顯示封面。必須是 `.jpg` / `.png`。

**AI 生圖的小字容易糊。** 高品質也不保證正確——實測 2K/high 那張反而糊了兩個字，
1K/low 那張全對。標題級的大字很穩，UI 註解那種小字要生成後逐字檢查。

**image-to-image 的 `quality` 預設是 `medium`，不是 `low`。** 本文上面那句「品質一律最低」
講的是 text-to-image 的預設。編輯端點照搬而沒顯式帶 `quality=low`，依上面的估算表就是
$0.004 → $0.015，**貴約 4 倍**。呼叫編輯端點時一定要顯式指定。

**Grok 的編輯端點沒有 `quality` 參數。** 也就是說成本無法靠參數壓低，也無法從規格預估——
要用它就得先小量實跑，比對 `GET /billing/balance` 的前後差額。

**Release 資產檔名會被剝掉非 ASCII 字元。** 與圖片無關但同一個坑：
GitHub Release 上傳 `劍人.epub` 會變成 `default.epub`。檔名一律用 ASCII。
